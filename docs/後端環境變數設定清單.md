# 後端環境變數設定清單（Zeabur 新 Backend Service）

> 給「在 Zeabur 建立新的 Node backend service，測試目前分支能否正確使用資料庫、並整合前端測試」這個當下用的**直接可操作清單**。
>
> 完整分析背景見 `specs/backend/production-env-readiness.md` §13、`specs/backend/zeabur-staging-runbook.md`——本檔案只抽出「現在要貼進 Zeabur console 的東西」，不重複整份分析。
>
> **安全原則：這個檔案不含任何真實 secret 值**——凡是要「沿用舊值」的變數，請自己對照 `環境變數.md`（那份檔案本身也不要 commit）手動複製貼上，本檔案只標註「抄哪一個 key」，不會把值也抄一份過來。

---

## 0. 你正在做的事，先確認一件事

你這次測試的資料庫，如果是 `環境變數.md` 裡那組 `DB_HOST=hkg1.clusters.zeabur.com`——**那是目前 Laravel 正在使用的正式資料庫，裡面是真實資料**（已用唯讀方式確認過：`users` 3 筆、`contact` 214 筆、`contact_class` 42 筆等）。

這件事本身**不是不能做**——schema 已經確認 100% 相容，這正是遷移專案想要的最終狀態（新 backend 接手同一份資料，不需要另外 export）。但要清楚意識到：

- ⚠️ 用這個新 backend service 測試時，任何 `POST`/`PUT`/`DELETE` 呼叫（例如 `POST /contact` 報名、`POST /admin/contact-class` 新增分類）**都會真的寫進正式資料庫**，不是測試用的假資料。
- 如果你想要的是「不動到真實資料」的測試，應該改用 `zeabur-staging-runbook.md` §3 規劃的**獨立 staging MySQL**，不是這組正式資料庫連線資訊。
- 如果你就是要驗證「新 backend 接上正式資料庫可以正常運作」——那就照下面清單直接設定即可，這正是這次要驗證的事。

以下清單假設你選擇**直接接正式資料庫**（因為你的問題是照著 `環境變數.md` 走）。若中途改變主意想換成獨立 staging DB，只需要把 §1 的 `DB_*` 四項換成你自己新建的 staging MySQL 連線資訊即可，其他項目不受影響。

---

## 1. 完整清單：需要在 Zeabur 新 backend service 貼上的環境變數

| # | Key | 動作 | 值怎麼來 |
|---|---|---|---|
| 1 | `NODE_ENV` | 新增 | 固定填 `production` |
| 2 | `PORT` | **第一輪先不要設** | 見 §2 |
| 3 | `DB_HOST` | 沿用 | 複製 `環境變數.md` 的 `DB_HOST` |
| 4 | `DB_PORT` | 沿用 | 複製 `環境變數.md` 的 `DB_PORT` |
| 5 | `DB_USER` | **改名沿用** | 值複製 `環境變數.md` 的 `DB_USERNAME`（**注意 key 名稱是 `DB_USER` 不是 `DB_USERNAME`**，這個最容易漏，漏了會直接啟動失敗） |
| 6 | `DB_PASSWORD` | 沿用 | 複製 `環境變數.md` 的 `DB_PASSWORD` |
| 7 | `DB_DATABASE` | 沿用 | 複製 `環境變數.md` 的 `DB_DATABASE` |
| 8 | `DB_CONNECTION_LIMIT` | 可選 | 不填會用預設值 `10`，通常不需要特別設 |
| 9 | `JWT_SECRET` | **全新產生** | **不可以**拿 `環境變數.md` 的 `APP_KEY` 來用——用途完全不同。自己跑 `openssl rand -hex 32` 產生一組新的，直接貼進 Zeabur，不要先貼在任何檔案/對話紀錄裡 |
| 10 | `JWT_EXPIRES_IN` | 新增 | 填 `30d` |
| 11 | `BCRYPT_SALT_ROUNDS` | 可選 | 不填會用預設值 `10` |
| 12 | `CORS_ALLOWED_ORIGINS` | 新增 | 見 §3，取決於你前端測試時用的網址 |
| 13 | `MAIL_HOST` | 見 §4 | 第一輪建議留空（見下） |
| 14 | `MAIL_PORT` | 見 §4 | 同上 |
| 15 | `MAIL_USERNAME` | 見 §4 | 同上 |
| 16 | `MAIL_PASSWORD` | 見 §4 | 同上 |
| 17 | `MAIL_ENCRYPTION` | 見 §4 | 同上 |
| 18 | `MAIL_FROM_ADDRESS` | 見 §4 | 同上 |
| 19 | `MAIL_FROM_NAME` | 見 §4 | 同上 |
| 20 | `RECIPIENT_EMAIL` | 見 §4 | 同上 |

**`環境變數.md` 裡其餘的變數（`APP_*`、`CACHE_DRIVER`、`QUEUE_CONNECTION`、`REDIS_*`、`SESSION_*`、`PUSHER_*`、`BROADCAST_DRIVER`、`LOG_CHANNEL`、`MAIL_DRIVER`、`DB_CONNECTION`、`PASSWORD`）全部不用搬，Node 程式碼裡沒有任何地方會讀它們。**

---

## 2. `PORT`：第一輪不要手動設定

`環境變數.md` 裡 Laravel 用的是 `PORT=${WEB_PORT}`——**這是舊 service 的設定，不代表新 backend 也需要**。Node 已經自己處理好 `process.env.PORT`（沒設定時預設 `8080`，`0.0.0.0` bind），先不要設，部署後看三件事：

1. Zeabur console 上這個 service 的 runtime env 有沒有自動出現 `PORT`
2. Deploy log 有沒有印出 `Server listening on 0.0.0.0:xxxx (production)`
3. `curl https://<這個新 service 的網址>/health` 打不打得通

三個都正常就不用管；只有 `/health` 打不通、且確定是 port 問題，才補上 `PORT=${WEB_PORT}` 試試看。

---

## 3. `CORS_ALLOWED_ORIGINS`：看你前端從哪裡測試

| 你測試前端的方式 | `CORS_ALLOWED_ORIGINS` 應該填 |
|---|---|
| 本機跑 `npm run dev`（`http://localhost:3000`）連這個新的 Zeabur backend | `http://localhost:3000` |
| 也在 Zeabur 建了一個新的前端 service | 那個前端 service 部署後拿到的網址（例如 `https://xxx.zeabur.app`） |

不確定的話，**先部署 backend、拿到 backend 網址後，才去處理前端那邊的 `NUXT_PUBLIC_API_BASE_URL`**，兩邊網址互相依賴，順序建議照 `zeabur-staging-runbook.md` §7。

不要填 `*`（程式碼本身也不支援 wildcard + `credentials:true` 這個組合）。

---

## 4. Mail：第一輪建議留空

- `MAIL_HOST` 留空即可（其餘 `MAIL_*`/`RECIPIENT_EMAIL` 也都不用填）——`MAIL_HOST` 空值時，寄信會被程式碼優雅跳過（log 一行警告），`POST /contact` 依然回 201 成功，不影響你要驗證的「資料庫能不能正常寫入」這件事。
- 如果你之後想連正式 SMTP 一起測（會寄出真的信），才把 `MAIL_*` 全部照 `環境變數.md` 的值填上，且 `MAIL_FROM_ADDRESS` 建議直接等於 `MAIL_USERNAME`（`環境變數.md` 裡沒有這個變數，Gmail SMTP 通常要求寄件人跟登入帳號一致）。
- ⚠️ 如果要測 `RECIPIENT_EMAIL`，那組值是**真實收件人**——填了之後任何 `POST /contact` 測試都會真的寄通知信過去，這點跟 §0 資料庫的提醒是同一件事：這是正式環境的資源，不是隔離的測試沙盒。

---

## 5. Health Check 設定

如果 Zeabur console 有「Health Check Path」欄位，填 `/health`，**不要**填 `/ready`（`/ready` 會查 DB，資料庫還沒連上前會一直不健康，可能讓 Zeabur 誤判部署失敗）。

---

## 6. 部署後驗證步驟（照順序）

```bash
curl https://<backend 網址>/health   # 期望 200
curl https://<backend 網址>/ready    # 期望 200，代表 DB 連線成功——這是你這次最想驗證的事
```

`/ready` 回 200 就代表「新 backend 可以正確使用這個資料庫」這件事已經驗證成功了。接著才是接前端、跑 E2E（清單見 `zeabur-staging-runbook.md` §8）。
